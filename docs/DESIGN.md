# Countersign — Mission Control design

Design direction: **security paper.** Bank security printing — check safety paper, guilloche,
blue-black ink, rubber stamps. Calm and precise like a well-run back office, with one memorable
moment: a stamp landing on a payment. This document is written before any component code, per
the mandated process. Part A (tokens/wireframes/components/motion/copy) comes first, Part B is
the anti-pattern review, Part C notes are added as built, Part D (screenshot critique) is appended
at the end after each shoot.

## Part A — tokens, wireframes, components, motion, copy

### A1. Color tokens (CSS variables, light theme only)

```css
--cs-paper:      #EDF1EC;  /* page background */
--cs-sheet:      #FBFCFA;  /* panels, documents, cards */
--cs-ink:        #1B2A41;  /* primary text */
--cs-ink-faded:  #5B6B7F;  /* secondary text, timestamps, captions */
--cs-rule:       #C9D6CC;  /* hairlines, guilloche strokes, dividers */
--cs-signature:  #2342A8;  /* primary actions, focus rings, countersigned state */
--cs-paid:       #2F6B4F;  /* stamp ink — paid only */
--cs-held:       #8F6214;  /* stamp ink — held only */
--cs-void:       #B3261E;  /* stamp ink — void/declined only */
```

Stamp inks are reserved for decisions. Nothing else on the page borrows `paid`/`held`/`void` —
that's what keeps them meaningful the instant a judge sees one.

### A2. Type tokens

- **Libre Franklin** — all product UI and all numbers. Weights 400 (body), 500 (labels/nav),
  600 (headings/amounts), 800 (stamps only). Tabular figures (`font-feature-settings:
  "tnum" 1`) on every amount, timestamp, and count.
- **Source Serif 4** — email and invoice content only. Rule: documents from outside the company
  are serif; Countersign's own voice is sans. That's the tell, at a glance, for what's untrusted.
- **Fragment Mono** — wallet addresses, tx hashes, invoice numbers only. Never a label, never a
  heading.
- **Mrs Saint Delafield** — one place only: the approver's name in the countersignature, wiped in
  left-to-right.

Scale: 12 / 13 / 15 / 18 / 24 / 36 (px). Lines under 80 characters. Sentence case everywhere.
Stamps are the only all-caps text in the product, because real stamps are.

### A3. Spacing and shape

Spacing scale: 4 / 8 / 12 / 16 / 24 / 32 / 48px. Shape follows what the object *is*, not one
global radius:

| Object | Radius | Edge treatment |
|---|---|---|
| Documents (email/invoice sheet) | 2px | 1px darker lower edge instead of a shadow |
| Decision card (ledger entry) | 6px | 3px left rule in the decision's stamp ink |
| Approval card (device) | 16px | none |
| Wallet row | 0 (table row) | 1px bottom hairline (`--cs-rule`) |
| Top bar / column shells | 0 | 1px hairline borders only |

No card gets a soft drop shadow. The only elevation cue anywhere is the document's 1px lower
edge and the decision card's left rule.

### A4. Guilloche (exactly three uses)

A procedural rosette — layered hypotrochoid curves, `stroke: var(--cs-rule)`, `stroke-width:
0.75`, no fill — generated by one `<Guilloche size seed />` component (parametric, seeded so it's
stable across renders, not random per mount). Used at:
1. 20px logo mark, top-left of the top bar.
2. A 6px-tall guilloche band under the top bar (full width, tiled).
3. A large, faint (8% opacity) watermark centered in empty states.

Nowhere else. If a fourth spot wants texture, the answer is a hairline, not a rosette.

### A6. Component list

- `TopBar` — wordmark + guilloche mark, `Tabs` (Mission Control / Attack Lab / Ledger / Under the
  hood — only Mission Control is live this prompt, others render a plain "not built yet" sheet),
  `GuardSwitch`, `RunInboxButton`, `ResetDemoButton`, environment tag, `UserMenu` (`DropdownMenu`).
- `GuardRule` — the 1px color rule under the guilloche band; void when guard is off, signature
  when on, with the note text beside it.
- `GuillocheMark` — the shared SVG rosette generator (logo / band / watermark are three sizes of
  the same component).
- `InboxColumn` → `InboxSlip` (one per email) → inline `SlipMarker` chips (amount / vendor
  change / hidden text / lookalike domain) → `SlipOutcomeGlyph` (small paid/held/void/declined
  mark once processed).
- `DocumentViewer` (`Dialog`) — `DocumentSheet` (serif render, DOMPurify-sanitized, isolated
  container), `HiddenTextToggle`, `ScanLine` (the reveal sweep), `ProvenanceHighlight` (span
  highlight when a provenance thread points here).
- `AgentActivityColumn` → `ActivityLine` (one per event, plain-English sentence + tabular
  timestamp) → `RawEventDisclosure` (technical payload, collapsed by default) → inline
  `DecisionCard` after every `payment_proposed`.
- `DecisionCard` → `DecisionHeader` (amount, payee, address+copy, invoice no.), `RiskBar` (ticks
  at 30/110, one segment per fired signal, `Tooltip` per segment), `Stamp` (the press animation),
  `Countersignature` (script wipe + "Confirmed on Solana in Xs" + explorer link), `TopReasons`,
  `TraceAddressButton`.
- `ProvenanceOverlay` — full-screen SVG portal, one bezier `ProvenanceThread` at a time.
- `ApprovalCard` (in the Money column's "Waiting on you") — binding message, `CountdownRing`,
  resolves in place then migrates into the activity timeline.
- `MoneyColumn` → `WalletRow` (×6, grouped Treasury / Vendors / Unrecognized wallets),
  `BalanceCount` (count-up number), `WaitingOnYou` (list of `ApprovalCard`s), `LastTwoRuns`
  (side-by-side stat pairs: stolen/paid/held/blocked).
- `EmptyState`, `LoadingSkeletons` (shaped like the real layout — inbox slip skeletons, activity
  line skeletons, wallet row skeletons), `ErrorNotice`.
- `AriaLiveAnnouncer` — one aria-live region, fed one sentence per decision.
- `ShortcutsHelp` (`Dialog`, opened by `?`).

### A7. Data flow

One zustand store (`useMissionControlStore`), fed by:
- `POST /api/runs` SSE stream → per-event reducer. On drop, fallback to polling
  `GET /api/runs/[id]/events?after=seq` every 2s until the stream (or run) recovers.
- `POST /api/approvals/poll` every 2s while any approval is pending.
- `GET /api/wallets` every 3s during a run, once more right after it finishes.
- `GET /api/inbox` once on load (see A8 — new route).

All money in the store stays `bigint` micro-units (non-negotiable #4); a single `formatUsd(micros)`
helper in `src/components/mission-control/format.ts` is the only place that divides by 1e6 and
calls `toLocaleString`.

### A8. New API surface (backend logic unchanged — additive only)

Two new read-only routes, both composed entirely from existing pure functions/queries. Documented
here and in `docs/PROGRESS.md`.

**`GET /api/wallets`** (in SPEC.md's route list already, just never built). Returns:
```
{
  wallets: [{ id, label, group: "treasury"|"vendor"|"unrecognized", address, musdcMicros }],
  recentRuns: [{ runId, mode, startedAt, stolenMicros, paidMicros, heldMicros, blockedMicros }]
}
```
Built from `getAllBalances()` + `loadWalletDirectory()` (unmodified) plus one new read-only
aggregate query over `payments` for the last two `runs` rows. Aggregation rule (UI concern, not a
policy change): `stolen` = confirmed tx to an attacker address; `paid` = confirmed tx to anyone
else; `blocked` = `decision = 'blocked'`; `held` = `decision` in
(`approval_pending`,`approved`,`denied`,`expired`) that never confirmed on-chain — this is what
lets a denied CEO-fraud request ($4,800 in the real E7 run) show up as money a human stopped,
instead of vanishing from the story.

**`GET /api/inbox?pack=demo`**. The Inbox column and Document Viewer need two things no existing
route serves: (1) which emails carry a hidden-text / lookalike-domain / vendor-change-request
marker, computed statically per email, and (2) email HTML annotated with `data-cs-hidden` so the
sanitized client render can toggle a reveal without a second server round trip. Returns:
```
{ emails: [{ id, position, fromName, fromAddress, subject, receivedAt,
             html,                 // DOMPurify-safe, spans wrapped data-cs-hidden="<reason>"
             markers: { invoiceAmountMicros: bigint|null, hasHiddenText, isLookalikeSender,
                        requestsVendorChange } }] }
```
Implemented with two new, additive exports — no existing export's behavior changes:
- `annotateHiddenHtml(html)` in `src/lib/countersign/htmlText.ts` — walks the same cheerio tree
  `renderNaiveEmail` reads, wraps hidden nodes (inherited hidden style, or a hit from the same
  zero-width regex) in `<span data-cs-hidden="reason">`, leaves every other node untouched.
  `renderNaiveEmail` itself is not touched.
- `computeInboxMarkers(email)` in a new `src/lib/countersign/inboxMarkers.ts` — composes
  `renderNaiveEmail` (hasHiddenText), `checkLookalikeSender` (isLookalikeSender), a max-`$`-amount
  regex over the rendered text (invoiceAmountMicros — the demo's invoices always list line items
  then a bolded total, so the largest figure in the email is always the total; verified against
  all 8 fixture emails), and a static keyword heuristic for "mentions changing a payout/remittance
  wallet" (requestsVendorChange — true for E2 and E5 only, checked by hand against the fixtures).

No other backend file changes. `pay_invoice`/`get_vendor`/etc. tool outputs are not modified —
where the UI wants a fact the agent's tools don't expose (e.g. "which email last changed this
vendor's payout address"), it's derived client-side by joining the run's own `vendor_change`
events against later `get_vendor` tool_results by address, never by adding fields to a tool result
the model would also see.

### A9. Signal families (risk bar color-coding — UI-only grouping, weights/keys unchanged)

| Family | Signals |
|---|---|
| Provenance (address identity) | `payee_unverified` (40), `untrusted_provenance` (15), `lookalike_sender` (30), `new_payee` (10) |
| History (spend pattern) | `recent_unverified_change` (25), `velocity_spike` (20), `amount_anomaly` (20), `duplicate_invoice` (hard block) |
| Content (what the email says) | `hidden_text` (25), `pressure_language` (5), `exec_impersonation` (15), `classifier_flag` (10), `hidden_only_payee` (hard block) |

Risk bar: 0–150 scale (max possible score with every soft signal firing is well under 150, so the
bar always has headroom before the 110 tick), ticks at 30 and 110, one segment per **fired**
signal only, width proportional to weight, fill color by family (three fixed, muted tints — not
the stamp inks, which stay reserved for decisions). Hard-block signals get a full-width void-ink
cap at the end of the bar when fired, since they bypass the score entirely.

### A10. Motion budget — exhaustive, nothing else animates

1. **Stamp press** — scale 1.08→1, rotate -4°→0°, 180ms, on decision.
2. **Signature wipe** — `clip-path` inset reveal, left→right, 700ms, on countersignature.
3. **Provenance thread** — `stroke-dashoffset` draw, ~350ms, on trace.
4. **X-ray scan line** — 2px signature-blue line sweeping down the sheet, ~450ms, on hidden-text
   reveal.
5. **Balance count-up** — numeric tween, on wallet balance change.
6. **Guard rule color change** — cross-fade between void/signature, on guard toggle.

No page-load stagger, no hover lift, nothing floats, no spinners. `prefers-reduced-motion`:
every one of the six renders its end state instantly, no exceptions.

### A11. Copy rules

- Plain, active, sentence case. "Paid $412.50 to Chesapeake Dairy Supply," not "Payment
  Processed Successfully."
- One name per concept through the whole flow: the button is always "Run inbox," the toast is
  "Inbox run started," never "Processing..." or "Executing agent run."
- Name things the way a judge understands them, not the way the code does: "Guard on," not
  "guarded mode enabled"; "Waiting on you," not "pending approvals."
- Event → sentence table (drives `ActivityLine`; raw payload always available behind the
  disclosure):

| Event kind | Sentence |
|---|---|
| `run_started` | "Started processing the inbox — guard {off/on}." |
| `email_read` | "Read {sender}'s email: “{subject}.”" |
| `tool_result` (`get_vendor`) | "Looked up {vendor}'s payout wallet: {addr}{, notes updated from {emailId} if a vendor_change in this run set that exact address}." |
| `tool_result` (`lookup_payment_history`) | "Looked up {vendor}'s payment history — {n} past payments." |
| `vendor_change` | "Updated {vendor}'s payout wallet from {old} to {new}, from {emailId} — not yet verified." |
| `payment_proposed` | "Proposed paying {amount} to {payee}." (immediately followed by the `DecisionCard`) |
| `risk_scored` | folded into the `DecisionCard`, not a separate line |
| `approval_requested` | "Sent to your phone: “{bindingMessage}.”" |
| `approval_resolved` (approved) | "You approved this payment." |
| `approval_resolved` (denied) | "You declined this payment." |
| `approval_resolved` (expired) | "The approval request expired." |
| `tx_submitted` | "Sending payment to Solana devnet…" |
| `tx_confirmed` | folded into the `DecisionCard`'s countersignature line |
| `payment_blocked` | "Blocked — {topReasons[0]}." |
| `agent_message` | shown verbatim, in the agent's own words, visually set apart (italic, ink-faded) |
| `error` | "Something went wrong: {message}." |
| `run_finished` | banner at the bottom of the activity column, not a timeline line |

- Empty: "8 emails in the inbox. Pick Guard off or Guard on, then run the inbox."
- Loading: skeletons only, shaped like the real layout.
- Errors say what happened and how it resolves: "Couldn't reach Solana devnet. Balances will
  refresh when it's back."

### A12. Keyboard

`G` guard toggle · `R` run inbox · `X` hidden-text toggle (document viewer open) · `P` presenter
mode (+15% type scale, raw tool calls hidden) · `?` shortcuts list. Visible focus rings, 2px,
`--cs-signature`, on every interactive element (Radix gives this almost for free; restyled, not
removed).

## Part B — anti-pattern review

Checked the plan above against each item before writing code:

1. **Near-black page + neon accent** — avoided: page is `--cs-paper` (#EDF1EC, light warm gray),
   the one saturated color (`--cs-signature`) is a muted blue used only for action/focus/guard-on,
   never a glow or accent wash.
2. **Cream + serif headline + terracotta** — avoided: serif is scoped to *external document
   content only* (a deliberate signal, not a headline aesthetic); no terracotta; headings are
   Libre Franklin.
3. **Identical rounded cards, same soft shadow** — avoided by A3's shape table: five different
   radii/edge treatments by object type, zero soft shadows anywhere.
4. **Gradients / glassmorphism** — avoided: every fill in the token set is a flat color; no
   backdrop-blur, no gradient stops planned anywhere.
5. **ALL-CAPS eyebrow labels** — avoided: sentence case everywhere except stamps, which earn
   their caps by being literal rubber-stamp text.
6. **Meta strings joined with middle dots** — avoided: the keyboard-shortcut line (A12) is the one
   place a middle dot would tempt; written as a plain list with `·` only between the shortcut
   *pairs* in the shortcuts dialog, not as inline metadata glue in the product surface itself. No
   "12 Feb · 3 signals · guarded" style strings anywhere.
7. **"Word - fragment" labels** — avoided: tab labels and buttons are short complete phrases
   ("Run inbox," "Reset demo"), not truncated fragments with a dash.
8. **Monospace for small labels** — avoided: Fragment Mono is scoped to addresses/hashes/invoice
   numbers only (A2); every label, tab, and button stays Libre Franklin.
9. **Arrows appended to button/link text** — avoided: "View on Solana Explorer" carries a lucide
   external-link *icon*, not a trailing "→" glyph in the string; "Run inbox" has no arrow.
10. **Fade-and-slide-up on every section** — avoided: motion budget (A10) has zero load animations
    at all; components mount in their end state.
11. **Hover lifts on every card** — avoided: not in the motion budget; cards don't move on hover,
    only focus/hover states change border/tooltip visibility.
12. **Emoji** — avoided: lucide-react icons only, 1.5 stroke.
13. **Lorem ipsum** — avoided: all copy in A11 and all wireframe content uses real demo-pack
    sentences (real vendor names, real amounts from the actual recorded runs).

**Changed from a first draft, and why:**
- Originally sketched the risk bar with a single flat fill; switched to family-colored segments
  (A9) because a flat bar reads as generic progress-bar chrome — a judge can't tell *why* a score
  is high without hovering every segment individually. Coloring by family gives an at-a-glance
  read ("mostly provenance-colored" vs "mostly content-colored") before any interaction.
- Originally planned to reuse `--cs-signature` for the risk bar's "ask a human" tick; changed to a
  neutral `--cs-ink-faded` tick mark instead, since blue is reserved for actions/focus/guard-on —
  reusing it on a static tick would dilute what blue means everywhere else on the page.
- Originally had the guilloche watermark at 20% opacity; dropped to 8% after re-reading the
  anti-pattern list's spirit (decorative elements should recede, not compete with real content in
  an empty state) — at 20% it read as a background texture rather than a quiet mark.
